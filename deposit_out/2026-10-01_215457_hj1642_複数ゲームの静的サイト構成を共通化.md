# 複数ゲームの静的研修サイトを共通構成へ整理する

## 再利用できる手順
- ルートの `index.html` はゲーム選択だけを担わせ、個別ゲームの解説を `games/<ゲーム名>/index.html`、振り返りを `games/<ゲーム名>/insight.html` に置く。入口と各コンテンツの責務が分かれ、ゲーム追加時の変更箇所を限定できる。
- 各ゲームフォルダに `index.html`、`insight.html`、`styles.css`、`assets/`、`previews/` を同じ名前で用意する。ゲーム名に依存しない規約にすることで、複製して追加できる。
- 全ゲームで使う見た目と動作は `shared/styles.css` と `shared/app.js` に集約し、ゲーム固有の色・図解だけを各 `styles.css` に残す。共通修正の重複を避けつつ、ゲームごとの個性を保てる。
- 共通JavaScriptでゲームごとの内容を切り替える場合は、`body` の `data-game` を識別子に使う。ファイルを複製せず、能力マップや保存キーだけを安全に切り替えられる。
- ファイル移動後は、全HTMLの `href` と `src` を抽出し、参照先の実在を機械検査する。ブラウザで見える画面だけを確認するより、下部や未操作状態の参照切れも拾いやすい。
- 最後にゲーム選択、各ゲームの解説、各振り返りを端末幅で開き、横はみ出し・ページ数・操作結果を数値と画像の両方で確認する。構造の正しさと実際の使いやすさを分けて検証できる。

## 会社環境の制約と回避策
- 通常のヘッドレスブラウザでは指定したスマホ幅と内部表示幅が一致しないことがあるため、Chrome DevTools Protocolで端末幅を明示的に上書きし、`scrollWidth` と `innerWidth` を比較した。
- 会社PCのブラウザ検証では一時プロファイルへのアクセスが制限される場合があるため、作業フォルダ内に用途限定のプロファイルを作り、非表示で起動した。検証後は対象プロセスとパスを確認してから削除した。

## 効かなかった / 遠回りだった試行
- PowerShellから長い `node -e` の正規表現を直接実行した → 引用符がPowerShell側で解釈され、参照検査が構文エラーになった → 短い検証用 `.mjs` を一時作成して実行し、完了後に削除した。
- URLの位置指定だけで下部セクションを撮影しようとした → 滑らかなスクロール中の別位置が撮影された → 検証時にスクロール動作を即時へ切り替え、対象要素へ移動してから撮影した。
- 既存ページをルート直下へ増やし続けた → ファイル名と役割がゲームごとに揃わず、次の追加で迷いやすくなった → 入口・共通部品・ゲーム別フォルダの三層に分離した。
